# ADR-001: Use PostgreSQL for Phoenix {status:Accepted|colour=Green}

{toc:maxLevel=2}

::: panel Context
The Phoenix payment platform needs a primary data store for transaction records,
customer payment methods, and reconciliation data. We need ACID guarantees for
financial data, sub-200ms query latency at 10K TPS, and compliance with EU data
residency requirements. The team has 5+ years of collective PostgreSQL experience
but limited NoSQL expertise.
:::

## Decision Drivers

- **Performance:** P99 < 200ms at 10K TPS for payment lookups
- **Consistency:** ACID required for financial transactions — eventual consistency is not acceptable
- **Team expertise:** 5+ years PostgreSQL across the team; limited Cassandra/DynamoDB experience
- **Compliance:** Data residency in EU (Frankfurt region)
- **Operational maturity:** Must have proven backup, replication, and monitoring tooling

## Options Considered

| Option | Pros | Cons | Effort | Cost/yr |
|--------|------|------|--------|---------|
| **PostgreSQL 16** | Familiar, ACID, rich ecosystem, JSONB for semi-structured data | Horizontal write scaling limits | M | $8K |
| **CockroachDB** | Distributed SQL, PostgreSQL wire-compatible, multi-region | Operational complexity, 3x cost, less tooling maturity | L | $24K |
| **Amazon DynamoDB** | Fully managed, auto-scaling, sub-10ms reads | Vendor lock-in, limited query flexibility, eventual consistency by default | M | $15K |

::: expand Detailed evaluation notes

### PostgreSQL 16
Tested with pgbench at 10K TPS on `db.r6g.xlarge`. P99 latency was 45ms for
simple lookups, 180ms for complex joins. Read replicas handle reporting queries
without impacting transaction throughput. PgBouncer connection pooling handles
connection management efficiently.

### CockroachDB
Evaluated CockroachDB Serverless. While PostgreSQL-compatible, we encountered
subtle query plan differences in complex CTEs. The 3x cost premium is hard to
justify for a single-region deployment. Would revisit for multi-region.

### DynamoDB
Strong for key-value access patterns but our reconciliation queries require
complex joins across payment records, merchant accounts, and settlement data.
Would need a secondary RDBMS for reporting, adding complexity.
:::

## Decision

**We will use PostgreSQL 16** on AWS RDS with the following architecture:

- **Primary:** `db.r6g.xlarge` in eu-central-1a for writes
- **Read replica:** `db.r6g.large` in eu-central-1b for reporting queries
- **Connection pooling:** PgBouncer with 200 max connections
- **Backup:** Automated daily snapshots + continuous WAL archiving to S3

```sql
-- Core schema pattern for payment records
CREATE TABLE payments (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    merchant_id UUID NOT NULL REFERENCES merchants(id),
    amount_cents BIGINT NOT NULL,
    currency VARCHAR(3) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'pending',
    provider VARCHAR(20) NOT NULL,
    provider_ref VARCHAR(255),
    metadata JSONB NOT NULL DEFAULT '{}',
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_payments_merchant ON payments(merchant_id, created_at DESC);
CREATE INDEX idx_payments_provider_ref ON payments(provider_ref) WHERE provider_ref IS NOT NULL;
```

## Consequences

> [!TIP]
> **Positive outcomes:**
> - Leverages existing team expertise — no training ramp-up needed
> - Rich monitoring ecosystem: pg_stat_statements, PgHero, pganalyze
> - JSONB column provides schema flexibility for provider-specific metadata
> - Proven backup and point-in-time recovery with RDS

> [!WARNING]
> **Risks to monitor:**
> - Write throughput ceiling at ~50K TPS on single primary. If we exceed this
>   within 18 months, we'll need to implement table partitioning by merchant_id
>   or consider Citus for distributed PostgreSQL.
> - Connection management is critical — PgBouncer misconfiguration can cascade.

> [!CAUTION]
> **Hard constraint:** We commit to PostgreSQL for payment data storage.
> Migrating away from PostgreSQL after GA would be a 6+ month effort.
> This decision should be revisited only if write throughput requirements
> exceed 50K TPS or multi-region active-active is needed.
